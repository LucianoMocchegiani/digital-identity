# 3.7 — Contrato de headers (a chequiar)

**Tarea BA:** Contrato de headers · **Estado entrega:** ✓ DONE (jun 2026)  
**Auditoría:** el gateway define e implementa el contrato HTTP de entrada/salida para el plano SCI (trazabilidad, autenticación, versión de API). La trazabilidad E2E por `correlationId` se detalla en [`1.5-contrato-correlation-id.md`](./1.5-contrato-correlation-id.md); este documento cubre el **conjunto de headers** y qué se reenvía al downstream.

---

## Lo implementado

### Headers que el cliente envía al gateway

| Header | Obligatorio | Uso | Comportamiento gateway |
|--------|-------------|-----|------------------------|
| `Authorization` | En rutas `requiresAuth: true` | `Bearer <JWT>` | `AuthGuard` → `POST /v1/auth/validate`; se reenvía al downstream vía proxy |
| `x-api-key` | Alternativa a Bearer | API key en claro (solo en tránsito TLS) | Mismo flujo validate; reenvío en proxy |
| `x-correlation-id` | Recomendado | ID de operación para auditoría | Si falta, `CorrelationIdMiddleware` lo deriva de `traceparent` o genera UUID |
| `traceparent` | Opcional | W3C Trace Context | Si falta, middleware genera `00-{traceId}-{spanId}-01` |
| `Accept` | Opcional | `text/event-stream` en rutas SSE | Gateway ajusta timeout y headers de respuesta streaming |

Rutas públicas (`/v1/auth`, `/v1/dids`): auth no obligatoria; si el cliente manda credenciales, el gateway intenta validate en modo opcional y adjunta `request.user` sin rechazar la petición.

### Headers que el gateway devuelve al cliente

| Header | Cuándo | Origen |
|--------|--------|--------|
| `x-correlation-id` | Siempre (middleware) | Generado o eco del entrante |
| `traceparent` | Siempre (middleware) | Generado o eco del entrante |
| `Deprecation`, `Sunset`, `Warning`, `Link` | Versión API `deprecated` | `ApiVersionInterceptor` (RFC 8594 / draft deprecation) |
| Headers de seguridad | Siempre | `helmet()` en `main.ts` |
| Headers del downstream | Respuestas proxy 2xx/4xx/5xx | Reenvío filtrado (sin hop-by-hop) |

### Headers reenviados al downstream (proxy)

`GatewayService.sanitizeHeaders` copia los headers entrantes **excepto** hop-by-hop:

- `host`, `connection`, `keep-alive`, `transfer-encoding`, `te`, `trailer`, `upgrade`
- `proxy-authorization`, `proxy-authenticate`
- `content-length` (Express re-serializa el body)

En la práctica el downstream recibe, entre otros:

- `Authorization` / `x-api-key` (si el cliente los envió)
- `x-correlation-id`, `traceparent` (inyectados o propagados por middleware)
- `user-agent`, `content-type`, etc.

**No se inyectan** headers derivados del contexto de auth validado (`X-Tenant-Id`, `X-App-Id`, `X-Api-Key-Id`, scopes). Esa decisión está documentada en el roadmap y en `deuda-tecnica/funcionalidades-pendientes.md`.

### Contexto de tenant sin header dedicado

Tras validate exitoso, `request.user` en gateway incluye `tenantId`, `appId`, `apiKeyId`, `scopes`, cuota (`plan`, `quotaLimit`, `quotaWindowMs`).

`TraceabilityInterceptor` publica auditoría a RabbitMQ con esos campos **más** `correlationId`. Los servicios downstream publican auditoría solo con el `x-correlation-id` recibido.

**Recuperar tenant en operations:** `GET /v1/operations/events?correlationId=` permite cruzar el evento del gateway (con `tenantId`) con eventos de index/auth/etc. del mismo ID — sin necesidad de `X-Tenant-Id` en el wire.

### Servicios downstream (eco y auditoría)

| Servicio | Lee `x-correlation-id` | Devuelve en respuesta | Audit con tenant |
|----------|------------------------|----------------------|------------------|
| quark-auth | `CorrelationIdInterceptor` (APP) | Sí | AuditInterceptor (sin tenant en payload) |
| quark-index, resolver | Interceptor + `req.correlationId` | Sí | AuditInterceptor |
| quark-operations | Solo en query API | No genera en HTTP | Consumer RabbitMQ |
| issuer / verifier / holder | Audit lee header | Parcial | Sin tenant si no hay header |

### Versión de API (relación 3.2)

El contrato de versión es **prefijo URI** `/v1/...`. No hay header `API-Version` de request; el ciclo de vida se comunica en **respuesta** vía `ApiVersionInterceptor` cuando una versión está `deprecated` o `sunset` (410).

## Matriz resumida (contrato MVP)

```
Cliente                    Gateway                         Downstream
───────                    ───────                         ──────────
Authorization  ──────────► validate + forward ────────────► (mismo header)
x-api-key      ──────────► validate + forward ────────────► (mismo header)
x-correlation-id ────────► CLS + forward ─────────────────► audit / logs
traceparent    ──────────► CLS + forward ─────────────────► (si aplica)
                           │
                           ├─► TraceabilityInterceptor → RabbitMQ (tenantId, …)
                           └─► NO X-Tenant-Id / X-App-Id en proxy
```

## Gaps detectados (a chequiar)

### 1. Sin spec formal única de headers

Reglas repartidas entre `AGENTS.md`, `auth-gateway-mvp.md`, README gateway y este directorio `a-chequiar/`. No hay tabla canónica “header → obligatorio → dirección” para integradores.

**Cierre sugerido:** `docs/http-headers-contract.md` o sección en README gateway con la matriz de arriba.

### 2. Contexto de auth no forwardeado (diseño conocido)

Downstream no recibe `X-Tenant-Id` ni scopes; depende de correlación en operations o de re-validar JWT localmente (no implementado).

Impacto: auditoría en index/issuer sin `tenantId`; RBAC fino imposible sin segunda validate (ver 2.3).

**Cierre sugerido:** inyectar headers de contexto en `GatewayService` tras `AuthGuard`, documentados y opcionalmente firmados.

### 3. Rate limit sin headers estándar

`TenantRateLimitInterceptor` responde 429 con body JSON (`limit`, `windowMs`) pero **no** setea `Retry-After` ni `X-RateLimit-*`.

**Cierre sugerido:** `Retry-After` en segundos según TTL Redis; opcional `X-RateLimit-Limit` / `Remaining`.

### 4. Doble publicación de auditoría en gateway

Coexisten `TraceabilityInterceptor` (con tenant) y `AuditInterceptor` (`source: quark-api-gateway`, sin tenant). Mismo `correlationId`, dos eventos por request.

**Cierre sugerido:** unificar en un solo interceptor o diferenciar `operation`/`source` en documentación.

### 5. Auth audit sin metadatos de tenant

`AuditInterceptor` de auth no incluye `tenantId` en el payload aunque el endpoint haya validado JWT — solo `correlationId` y operación.

**Cierre sugerido:** enriquecer payload cuando `req.user` exista (endpoints protegidos con `JwtAuthGuard`).

### 6. Tráfico directo a puertos internos

Wallet y OID4VC pueden omitir gateway; entonces no aplican middleware de headers del gateway (solo lo que envíe el cliente).

Ver gaps de 1.5 (issuer/verifier/holder, wallet).

### 7. Solapamiento con 1.5

Cambios en trazabilidad deben actualizarse en **ambos** documentos o consolidarse en la spec formal (gap 1).

## Situación por capa (resumen)

El **contrato de headers del MVP** está **centrado en el gateway**: el cliente manda credenciales + trazabilidad; el gateway valida, enriquece trazas y reenvía credenciales y correlation al downstream.

La **excepción deliberada** es no forwardear contexto de tenant como headers HTTP: se compensa con auditoría del gateway y query por `correlationId` en operations.

Para integradores, lo esencial es: **`Authorization` o `x-api-key`**, **`x-correlation-id`** (recomendado), rutas bajo **`/v1`**.
