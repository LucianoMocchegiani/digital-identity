# 3.6 — Normalización de errores (a chequiar)

**Tarea BA:** Normalización de errores en gateway y ecosistema · **Estado entrega:** ✓ DONE (jun 2026)  
**Auditoría:** el gateway normaliza errores **propios**; las respuestas de error de servicios downstream se reenvían **sin transformar** vía proxy. Hay filtros globales en la mayoría de servicios, pero el **shape JSON no es uniforme** entre módulos.

---

## Lo implementado

### quark-api-gateway

**Errores locales.** `GlobalExceptionFilter` registrado en `AppModule` (`APP_FILTER`). Para excepciones lanzadas en el gateway (ruta no encontrada, circuit breaker abierto, timeout tras reintentos, fallo de proxy sin respuesta downstream) el cliente recibe JSON con:

- `statusCode`
- `timestamp` (ISO)
- `path`
- `message`
- `correlationId` (desde header entrante)
- `details` (opcional, si la excepción lo trae)

**Errores downstream (proxy).** `GatewayService.forwardErrorResponse` reenvía status, headers y **body en streaming tal cual** lo devolvió el microservicio (`error.response.data.pipe(res)`). No pasa por `GlobalExceptionFilter`.

Comportamiento deliberado para **transparencia del servicio origen** y para no parsear streams de error arbitrarios; implica que el contrato de error **no está unificado** en rutas proxyadas.

**Casos cubiertos por el filtro del gateway:** 404 sin ruta en tabla, 503 circuit breaker, 503 timeout, 500 error interno de proxy.

### Servicios SCI (auth, index, resolver, operations, observer)

Patrón `AllExceptionsFilter` en `main.ts`: `statusCode`, `timestamp`, `path`, `correlationId`, `message`.

El campo `message` a veces es el **objeto completo** de `getResponse()` (p. ej. validación Nest con `{ message: string[], error: string }`), no un string plano.

### Servicios de identidad (issuer, verifier)

`GlobalExceptionFilter` en `http-exception.filter.ts`: `statusCode`, `message` (desde `exception.message`, no siempre el body rico de `getResponse()`), `path`, `timestamp`. Sin `correlationId` ni `errorCode` en el body.

### quark-holder-service

Implementación más completa: `statusCode`, `message`, `error` (nombre HTTP), `errorCode` (dominio opcional), `details` (validación), `path`, `timestamp`. Logging diferenciado WARN/ERROR.

## Gaps detectados (a chequiar)

### 1. Proxy sin normalización (gap principal del roadmap)

Cualquier `4xx`/`5xx` con body del downstream llega al cliente con el shape que definió ese servicio. El gateway solo añade normalización cuando **él** lanza la excepción.

**Impacto:** SDKs y clientes deben tolerar varias formas de error según ruta (`/auth` vs `/issuers` vs `/index`).

**Cierre sugerido:** capa opcional en `forwardErrorResponse` que parsee JSON y mapee a un contrato único (p. ej. el de holder) + siempre inyectar `correlationId` del request entrante.

### 2. Shapes inconsistentes entre servicios

| Servicio | correlationId en body | Campo `error` | `errorCode` / `details` |
|----------|----------------------|---------------|-------------------------|
| Gateway (local) | Sí | No | details opcional |
| Auth, Index, … | Sí | No | message puede ser objeto |
| Issuer, Verifier | No | No | No |
| Holder | No (en filtro actual) | Sí | Sí |

No hay documento de contrato de error único en `docs/` ni DTO compartido en `@quarkid/auth` o SDK.

### 3. Auth `message` como objeto anidado

`AllExceptionsFilter` asigna `message: exception.getResponse()` sin aplanar arrays de validación. El cliente puede recibir `message: { message: [...], error: "Bad Request" }`.

**Cierre sugerido:** alinear auth (y SCI) al `extractPayload` de holder.

### 4. Éxitos proxy vs errores proxy

Respuestas 2xx también se pipean sin tocar; solo los errores son relevantes para 3.6. Coherente.

### 5. Errores de red sin respuesta HTTP

Tras agotar reintentos sin `error.response`, el gateway lanza `ServiceUnavailableException` o `InternalServerErrorException` → **sí** normalizados por `GlobalExceptionFilter`. Bien cubierto.

---

## Situación por capa (resumen)

La tarea BA se cumple en el **mínimo viable**: filtro global en gateway para fallos del propio componente y filtros en servicios downstream. Falta la **capa de unificación en el perímetro** cuando el error nace detrás del proxy.

Para MVP, documentar el contrato “error local gateway vs error reenviado” es aceptable; la unificación estricta es mejora incremental.

---

## Prioridad de cierre opcional

**P1 — Contrato documentado** en README gateway o `docs/`: campos mínimos esperados y tabla de servicios.

**P2 — Normalizador en `forwardErrorResponse`** para bodies JSON (no stream opaco).

**P2 — Alinear SCI + auth** al shape de holder (`message` string + `details` para validación).

**P3 — `correlationId` en body** de issuer/verifier/holder cuando el header ya existe.
