# 2.6 — Política de expiración de tokens (a chequiar)

**Tarea BA:** Política de expiración de tokens · **Estado entrega:** ✓ DONE (jun 2026)  
**Auditoría:** expiración JWT operativa vía `JWT_EXPIRES_IN`, verificación en `validate` y revocación de API keys. Lo que sigue completa el ciclo de vida (revocación JWT explícita, coherencia de `expires_in`).

---

## Lo implementado

### JWT — emisión y expiración

**TTL configurable.** `JwtModule` registra `signOptions.expiresIn` desde `JWT_EXPIRES_IN` (default `1h` en `environment.config.ts`). Cada token firmado lleva claim `exp` estándar.

**Identificador único.** En cada emisión se genera `jti` (UUID v4) dentro del payload, lo que permite revocación puntual si se registra en `revoked_tokens`.

**Respuesta de token.** `POST /v1/auth/token` devuelve `access_token`, `token_type: Bearer`, `scope` y metadatos de tenant.

### JWT — validación

**Expiración automática.** `jwt.verify()` en `validateToken` rechaza tokens vencidos (`Invalid or expired token`).

**Lista de revocados.** Si el payload incluye `jti`, se consulta la tabla `revoked_tokens`; si existe fila, responde 401 `Token revoked`. La entidad guarda `jti`, `expires_at` y `revoked_at` (schema en `database/db_creation_script.sql`).

### API keys — expiración y revocación

**Revocación operativa.** `DELETE /v1/auth/keys/:id` marca `is_revoked = true`; `resolveApiKey` excluye keys revocadas.

**Expiración en modelo.** La columna `expires_at` existe en `api_keys`; `validate` rechaza keys con fecha pasada (`API key expired`).

**Alta de keys.** `POST /v1/auth/keys` crea keys con hash y prefijo; no expone el valor tras la creación.

## Gaps detectados (a chequiar)

### 1. `expires_in` hardcodeado en la respuesta

`TokensService.issue` devuelve siempre `expires_in: 3600` aunque `JWT_EXPIRES_IN` sea distinto (p. ej. `2h` o `15m`).

Consecuencia: clientes OAuth que confían en `expires_in` para renovar pueden desincronizarse del `exp` real del JWT.

**Cierre sugerido:** calcular `expires_in` desde `config.get('jwt.expiresIn')` o decodificar el `exp` del token recién firmado.

### 2. Sin endpoint de revocación JWT

La tabla `revoked_tokens` y el chequeo en `validate` existen, pero **ningún servicio escribe** en esa tabla. No hay `POST /v1/auth/revoke`, logout ni revocación por `jti`.

Consecuencia: un JWT robado sigue válido hasta su `exp` natural; la infra de revocación está a medias.

**Cierre sugerido:** `POST /v1/auth/revoke` (Bearer del token a invalidar o admin con `jti`) → insert en `revoked_tokens` con `expires_at` = `exp` del JWT. Prerrequisito útil para cache Redis (2.5).

### 3. API keys sin TTL en el alta

`CreateApiKeyDto` no acepta `expiresAt`; `create` siempre deja `expires_at` en null (sin vencimiento).

La política de expiración para keys está en el modelo pero no expuesta al operador.

**Cierre sugerido:** campo opcional `expiresIn` o `expiresAt` en el DTO de creación.

### 4. Sin limpieza de `revoked_tokens`

No hay job que borre filas cuyo `expires_at` ya pasó (el token ya no sería aceptado por `exp` de todas formas).

**Cierre sugerido:** cron o `DELETE` periódico `WHERE expires_at < NOW()` — housekeeping, no bloqueante MVP.

### 5. Sin refresh tokens ni rotación

Política actual: access token único, sin `refresh_token`, sin rotación de `clientSecret` automatizada.

Aceptable para MVP machine-to-machine; documentar como límite si BA pide sesiones largas.

### 6. Sin TTL diferenciado por tenant

Un solo `JWT_EXPIRES_IN` global; no hay política por `tenant.type` o plan.

**Cierre sugerido:** solo si negocio lo pide; por ahora config global alcanza.

## Situación por mecanismo (resumen)

**JWT:** expira solo por tiempo (`exp`) — funciona. Revocación anticipada preparada en schema pero sin API que la active.

**API key:** revocación manual sí; expiración por fecha solo si se cargara `expires_at` (hoy no se setea en create).

**Gateway:** no participa en política de expiración; delega en auth vía validate (token expirado → 401 aguas abajo).

---

## Prioridad de cierre opcional

**P1 — Revocación JWT.** Endpoint + insert `revoked_tokens`; habilita logout operativo y desbloquea 2.5 (cache) con invalidación coherente.

**P1 — `expires_in` dinámico.** Alinear respuesta de `/token` con `JWT_EXPIRES_IN`.

**P2 — TTL en creación de API key.** Campo opcional en DTO.

**P3 — Purga de revocados expirados.** Mantenimiento de tabla.
