# 1.5 — Contrato de correlationId (a chequiar)

**Tarea BA:** Contrato de correlationId · **Estado entrega:** ✓ DONE (jun 2026)  
**Auditoría:** el núcleo del contrato está operativo en el plano SCI vía gateway. Lo que sigue son mejoras para trazabilidad E2E completa, no bloqueantes para el cierre de entrega.

---

## Lo implementado

### quark-api-gateway

**Generación y propagación.** `CorrelationIdMiddleware` crea o reutiliza `traceparent` (W3C Trace Context) y `x-correlation-id`, los guarda en contexto async (CLS), los inyecta en `req.headers` y los devuelve en la respuesta al cliente.

**Proxy downstream.** `GatewayService` reenvía headers saneados (`sanitizeHeaders`), incluidos `x-correlation-id` y `traceparent`, hacia auth, index, resolver y el resto de rutas configuradas.

**Auditoría en gateway.** `TraceabilityInterceptor` publica eventos en RabbitMQ con `correlationId` tomado del CLS; si hubo JWT validado, adjunta `tenantId`, `appId` y `apiKeyId`.

### Plano SCI (auth, index, resolver)

**Interceptores HTTP.** `CorrelationIdInterceptor` asegura un ID por request (header entrante o UUID nuevo) y lo refleja en la respuesta. `AuditInterceptor` lee `x-correlation-id` y publica operación, latencia y estado a la cola de auditoría.

**Cadena index → resolver.** En `GET /v1/index/dids/:did`, el controller pasa `req.correlationId` al cliente HTTP del resolver, que incluye `x-correlation-id` en el fetch on-demand cuando el DID no está en caché ni en Postgres.

### quark-operations

**Persistencia y consulta.** El consumer de RabbitMQ guarda `correlationId` en Postgres. La API expone `GET /v1/operations/events?correlationId=` para recuperar el timeline de eventos de una operación.

### Herramientas y documentación operativa

Las colecciones Postman generan `x-correlation-id` en pre-request si el campo está vacío (`postman/README.md`, `docs/auth-gateway-mvp.md`).

Con RabbitMQ activo, el flujo **Postman → gateway → auth / index / resolver** es consultable en operations por el mismo ID.

## Gaps detectados (a chequiar)

### 1. Spec formal única

No hay documento de contrato dedicado. Las reglas están repartidas entre `AGENTS.md`, `auth-gateway-mvp.md` y documentos de visión del producto.

**Cierre sugerido:** `docs/correlation-id-contract.md` con nombre del header, relación con `traceparent`, cuándo genera el gateway vs cuándo debe enviar el cliente, y cómo consultar en operations.

### 2. Servicios de identidad sin generar ID

En **issuer (9001), verifier (9002) y holder (9005)** hay `AuditInterceptor` pero no `CorrelationIdInterceptor` registrado.

La wallet y los flujos OID4VC entran **directo** al puerto del servicio, sin pasar por el middleware del gateway. Si no llega header, la auditoría persiste `correlationId: 'unknown'`:

```typescript
// quark-issuer-service/source/src/messaging/audit.interceptor.ts
const correlationId = Array.isArray(raw) ? raw[0] : (raw ?? 'unknown')
```

**Cierre sugerido:** registrar `CorrelationIdInterceptor` en issuer, verifier y holder; que `quark-wallet` envíe `x-correlation-id` (UUID por flujo OID4VCI/VP).

### 3. Observer y operations HTTP

**Observer:** el interceptor de correlation existe en código pero no está registrado en `main.ts` — solo corre `LoggingInterceptor`.

**Operations:** la API HTTP no genera ni devuelve `x-correlation-id`; el servicio solo consume eventos de RabbitMQ.

**Cierre sugerido:** alinear observer con index/resolver; opcional interceptor en operations para requests directos a la API de eventos.

### 4. Logs JSON sin `correlationId`

`JsonLoggerService` y `LoggingInterceptor` emiten JSON o texto sin el campo `correlationId` en cada línea de request (relacionado con la tarea **1.4** Logging estructurado).

El contrato deseado en `AGENTS.md` es `{ service, endpoint, status, latency, correlationId }` — hoy no se cumple en la mayoría de servicios al correlacionar logs con operations.

**Cierre sugerido:** leer `req.correlationId` o header en `LoggingInterceptor` y añadirlo al objeto JSON de log.

### 5. identity-core saliente

Las llamadas HTTP desde `@quarkid/identity-core` hacia el KMS externo no reenvían `x-correlation-id` (ver `docs/deuda-tecnica/identity-core-manejo-produccion.md`).

**Cierre sugerido:** thread-local o parámetro de contexto en clients HTTP del SDK servidor.

### 6. Menores

**Doble auditoría en gateway.** Coexisten `TraceabilityInterceptor` y `AuditInterceptor`; pueden publicar dos eventos por request con `source` distinto (`gateway` vs `quark-api-gateway`).

**traceparent vs x-correlation-id.** Solo el gateway unifica ambos; el resto del SCI trabaja casi solo con `x-correlation-id`.

**Eventos DID en RabbitMQ.** `DidEventPayload.correlationId` es opcional; los publicadores no siempre lo incluyen.

**Explorer.** La API de timeline por `correlationId` existe en operations; la UI del explorer aún no la consume (ítem **8.4** en `deuda-tecnica/roadmap-extensiones-deuda.md`).

## Situación por capa (resumen)

En **quark-api-gateway** el header se genera o propaga correctamente y hay auditoría hacia operations (con el matiz del doble interceptor). Los logs HTTP no incluyen `correlationId`.

En **quark-auth, quark-index y quark-resolver** el patrón interceptor + audit está cableado de punta a punta para tráfico que entra por HTTP. Tampoco hay `correlationId` en logs JSON.

En **quark-observer** la auditoría funciona si llega el header, pero no se garantiza generación local porque falta registrar el interceptor.

En **quark-operations** solo actúa como consumidor y API de consulta; no participa en la cadena HTTP entrante.

En **issuer, verifier y holder** la auditoría publica con `unknown` si la wallet o un cliente directo no envía header.

**quark-wallet** no envía `x-correlation-id` en sus llamadas HTTP al ecosistema.

**identity-core** no propaga el header en salidas HTTP internas.

## Prioridad de cierre opcional

**P0 — Spec formal.** Un solo documento de contrato en `docs/` para integradores y operaciones.

**P1 — Identidad y wallet.** `CorrelationIdInterceptor` en issuer, verifier, holder; wallet manda `x-correlation-id` por flujo OID4.

**P1 — Observer y operations HTTP.** Registrar interceptor en observer; valorar lo mismo en operations para simetría.

**P2 — Logs JSON.** Incluir `correlationId` en `LoggingInterceptor` de cada servicio (alinea con 1.4).

**P3 — Limpieza y profundidad.** Unificar audit del gateway; propagar header en HTTP saliente de identity-core; cablear explorer a `operations/events`.
