# 2.5 — Caché de tokens en Redis (análisis)

**Tarea BA:** Caché de tokens en Redis · **Estado entrega:** BACKLOG  
**Objetivo del documento:** decidir si conviene implementar Redis en `quark-auth` para validación de tokens, o cerrar la tarea de otra forma.

---

## Situación actual

**Dependencia sin uso.** `ioredis` está en `package.json` de `quark-auth` y `environment.config.ts` define `redis.host`, `redis.port` y `redis.ttl` (3600 s). Docker Compose levanta Redis y pasa `REDIS_HOST` / `REDIS_PORT` al servicio auth. **No hay ningún módulo, servicio ni import de Redis en `quark-auth/src`.**

**Validación JWT hoy.** `TokensService.validateToken` hace `jwt.verify` en memoria (HMAC con `JWT_SECRET`). Solo toca Postgres si el payload trae `jti`: una lectura a `revoked_tokens` por clave primaria. No hay round-trip a DB para el caso “token válido y no revocado”.

**Validación API key.** `validateApiKeyOnly` / flujo con `x-api-key` sí va a Postgres (búsqueda por prefijo + `bcrypt.compare` por candidato). Es el camino más caro, pero suele usarse menos que el JWT Bearer en el hot path del gateway.

**Gateway.** En cada request a ruta con `requiresAuth: true`, `AuthGuard` hace **HTTP POST** a `quark-auth` `/v1/auth/validate`. Eso añade latencia de red y carga al servicio auth aunque la validación JWT sea barata. El gateway **sí** usa Redis, pero solo para **rate limit por tenant** (`TenantRateLimitInterceptor`), no para cachear tokens.

**Visión de producto.** `QuarkID_2.0.md` describe Auth con “cachea en Redis” y el health readiness futuro de auth incluye Redis (`funcionalidades-pendientes.md`), aunque hoy el servicio funciona sin él.

---

## Qué pretendía la tarea 2.5 (contrato BA)

Típicamente “caché de tokens en Redis” en este stack implica una o más de:

1. **Cachear el resultado de `validate`** — clave = hash del token o `jti`, valor = `AuthContext` serializado, TTL = tiempo restante del JWT.
2. **Lista de revocados en Redis** — set o clave por `jti` con TTL, para no consultar Postgres en cada validate.
3. **Cachear resolución de API key** — tras bcrypt exitoso, guardar contexto por prefijo/id (menos común).

Ninguna de las tres está implementada.

---

## ¿Tiene sentido incorporar Redis? Veredicto

**Para el MVP y la carga actual: no es prioritario.**  
**Para producción con mucho tráfico o como cierre del contrato BA: sí tiene sentido, pero con alcance acotado y después de resolver revocación (2.6).**

### Por qué NO es urgente ahora

**JWT ya es stateless.** Verificar un HMAC local es barato (microsegundos). El cuello de botella real no es Postgres en validate JWT, sino el **salto HTTP gateway → auth en cada request**. Cachear en auth no elimina ese salto; solo hace más rápida la respuesta de auth cuando llega.

**Revocación incompleta (2.6).** Existe tabla `revoked_tokens` pero no hay endpoint público de revocación ni invalidación coordinada. Si se cachea `AuthContext` en Redis sin estrategia de purge al revocar, un token revocado seguiría siendo aceptado hasta que expire el TTL del cache — peor que el estado actual.

**Redis ya está “de mentira” en auth.** Mantener `ioredis` + env + `depends_on: redis` sin código añade complejidad operativa (otro punto de fallo en readiness) sin beneficio. O se usa o se limpia.

**Escala MVP.** Pocas apps, tokens de 1 h, validate idempotente: Postgres aguanta sin problema.

### Por qué SÍ tendría sentido (más adelante)

**Volumen de validate.** Si cada llamada al gateway dispara validate y hay muchos RPS, cachear por `jti` reduce CPU repetida y la query a `revoked_tokens` en tokens “calientes”.

**Revocados en Redis.** Con endpoint de revocación (2.6), un `SET revoked:{jti}` con TTL = exp del token permite check O(1) y coherencia si al revocar se borra también `cache:validate:{jti}`.

**API keys.** Cachear el `AuthContext` tras validar una API key (TTL corto, p. ej. 5–15 min) evita bcrypt + Postgres en cada request con `x-api-key` — ahí Redis sí aporta más que en JWT puro.

**Alineación con diseño original.** Cierra 2.5, justifica Redis en compose para auth y habilita health `PostgreSQL + Redis` como en el checklist de deuda técnica.

**Coherencia con el ecosistema.** Index ya usa Redis para caché de DIDs; el patrón infra está asentado.

---

## Alternativa con más impacto que solo cache en auth

Antes (o además) de Redis en auth, valorar **validación local en gateway**:

- Gateway verifica JWT con el mismo `JWT_SECRET` (o JWKS si migran a asimétrico).
- Comprueba `exp` y opcionalmente consulta revocados (Redis compartido o llamada batched a auth).
- Elimina un HTTP por request — ganancia mayor que cachear validate en auth.

Eso es diseño distinto al actual (“auth como única fuente de verdad vía `/validate`”) pero es el patrón habitual en API gateways de alto tráfico.

## Recomendación práctica

| Opción | Cuándo | Acción |
|--------|--------|--------|
| **A — Deferir (recomendado MVP)** | Carga demo / entrega actual | Dejar 2.5 en BACKLOG o mover a deuda técnica; **quitar** `ioredis` y `depends_on: redis` de auth si no se va a usar pronto (reduce ruido). |
| **B — Implementación mínima** | Cerrar contrato BA / tráfico medio | Tras 2.6 (revocación): cache `validate` por `jti`, TTL = `exp - now`; al revocar, `DEL` cache + set revocado; módulo `RedisModule` como en index. |
| **C — Gateway-first** | Performance E2E | JWT verify en gateway + Redis compartido solo para revocados; auth queda para emisión y administración de keys. |

**No recomiendo** marcar 2.5 como DONE sin código ni marcar DONE “porque JWT no lo necesita” sin actualizar el contrato/roadmap — la infra y la dependencia sugieren que BA esperaba Redis activo.

## Si se implementa (especificación mínima)

**Claves sugeridas**

- `auth:validate:jti:{jti}` → JSON `AuthContext`, TTL = segundos hasta `exp`.
- `auth:revoked:jti:{jti}` → `1`, TTL = igual al token (complemento o reemplazo de Postgres).

**Flujo validate**

1. Extraer `jti` del JWT (tras verify) o hash del token.
2. Si existe en `revoked` → 401.
3. Si hit en `validate` → devolver cache.
4. Si miss → lógica actual; en éxito, `SET` con TTL.

**Invalidación**

Al revocar: escribir revocado + borrar cache. Obligatorio antes de confiar en cache.

**API key (opcional fase 2)**

`auth:apikey:{prefix}:{id}` con TTL corto tras bcrypt OK.
