# 4.8 — Negociación de content-type (a chequiar)

**Tarea BA:** Negociación de content-type · **Estado entrega:** ✓ DONE (jun 2026)  
**Auditoría:** la validación de `Accept` y el rechazo **406** están implementados en **quark-resolver** (`GET /v1/dids/resolve/:did`). La respuesta HTTP usa siempre `Content-Type: application/json` (envoltorio W3C); el tipo negociado aparece solo en `didResolutionMetadata.contentType`, fijo en `application/did+ld+json`.

---

## Lo implementado

### quark-resolver — validación de `Accept`

**Endpoint:** `GET /v1/dids/resolve/:did` (también vía gateway `GET /v1/dids/resolve/:did`).

**Tipos soportados** (`ResolverService`, constante `SUPPORTED_TYPES`):

- `application/json`
- `application/did+json`
- `application/did+ld+json`

**Regla:** si el cliente envía header `Accept` y **ninguno** de los tipos anteriores aparece como substring en el valor, se lanza `NotAcceptableException` → **HTTP 406** con cuerpo:

```json
{
  "error": "notAcceptable",
  "message": "Supported types: application/json, application/did+json, application/did+ld+json"
}
```

**Sin header `Accept`:** no se valida; la resolución continúa (comportamiento permisivo para clientes simples).

**Controller:** `@Headers('accept')` en `ResolverController.resolve`; el DID se extrae de `req.originalUrl` sin decodificar (preserva `%3A` en `did:web`).

### Respuesta HTTP y metadata W3C

**Cuerpo:** estructura W3C DID Resolution v0.3 — `didDocument`, `didDocumentMetadata`, `didResolutionMetadata`.

**Header HTTP `Content-Type`:** Nest/Express serializa el JSON con **`application/json`** por defecto; no se setea `@Header()` ni `res.type()` según `Accept`.

**`didResolutionMetadata.contentType`:** en resoluciones exitosas, `buildResolutionResult` fija **`application/did+ld+json`** siempre, independientemente del `Accept` enviado.

**Otros campos metadata:** `source` (`index` | `did:web` | `algorithmic`), `retrieved` (ISO timestamp).

### Gateway

El proxy reenvía el header `Accept` del cliente al resolver (`sanitizeHeaders`). No transforma content-type en la respuesta: pipe del downstream tal cual (ver 3.6).

### Integración quark-index

`ResolverClientService` llama al resolver con `accept: application/did+json` en el fetch on-demand (cascada Redis → Postgres → resolver).

**`GET /v1/index/dids/:did`** no implementa negociación `Accept`; devuelve el DTO del index (`DidRecordResponseDto`) siempre como JSON de aplicación.

### Publicación did:web (relación 4.3 / 4.15)

**Issuer / verifier:** `GET /:walletId/did.json` (sin `/v1`) devuelve el documento DID como JSON Nest; sin validación `Accept`.

Los documentos en `/.well-known/did.json` vía HTTP `did:web` dependen del servidor origen (identity-core / Credo), no del resolver.

### Pruebas y documentación

- Postman `Quark-Flujos-DIDComm-OID4VC` — sección `00.R Resolver`: requests con `Accept: application/did+ld+json` y caso **00.R7** (`application/xml` → 406, `error: notAcceptable`).
- README `quark-resolver` documenta flujo “Validar Accept header” y ejemplos curl.

## Gaps detectados (a chequiar)

### 1. Negociación solo en entrada, no en salida

El roadmap resume bien el MVP: **valida `Accept` (406)** pero **respuesta HTTP siempre `application/json`**.

Un cliente que pide `application/did+json` recibe el envoltorio W3C con `Content-Type: application/json`, no el documento “crudo” con el media type DID.

**Cierre sugerido:** tras validate, setear `Content-Type` en respuesta según el tipo elegido; opcionalmente devolver solo `didDocument` para `application/did+json` (breaking change — documentar).

### 2. Metadata `contentType` no refleja `Accept`

Siempre `application/did+ld+json` en éxito aunque el cliente pidió `application/json` o `application/did+json`.

**Cierre sugerido:** mapear el primer tipo compatible del `Accept` al campo metadata (y al header HTTP si se implementa gap 1).

### 3. Matching naive con `includes`

`accept.includes(t)` acepta valores compuestos tipo `application/json;q=0.9` (OK) pero rechaza `*/*` con **406** aunque muchos clientes HTTP lo envían por defecto.

**Cierre sugerido:** parser de `Accept` (q-values) o tratar `*/*` y ausencia de header como “cualquier tipo soportado”.

### 4. Index y did.json sin negociación

`GET /v1/index/dids/:did` y `GET /:walletId/did.json` no validan `Accept`. Solo el resolver cumple el contrato BA de esta tarea.

**Cierre sugerido:** documentar que 4.8 aplica al **resolver**; o reutilizar `SUPPORTED_TYPES` en index para paridad.

### 5. Errores 406 con shape distinto al éxito

406 pasa por `AllExceptionsFilter` → `{ statusCode, timestamp, path, correlationId, message }` donde `message` puede ser el objeto `{ error, message }`. No es el mismo shape que `didResolutionMetadata` en éxito (coherente con 3.6 / 4.9).

### 6. Sin `Vary: Accept`

Respuestas cacheables (CDN/proxy) no declaran variación por `Accept`.

**Cierre sugerido:** `Vary: Accept` si se implementa content-type de respuesta variable.

---

## Situación por capa (resumen)

Para el **contrato BA de negociación DID**, el único componente que implementa el ciclo **request `Accept` → 406 o 200** es **quark-resolver**.

El MVP cumple **rechazo de tipos no soportados** y documentación operativa; **no** cumple negociación HTTP completa (header de respuesta alineado al `Accept`).

Index, gateway y publicación `did.json` son JSON genérico sin esta capa.

---

## Prioridad de cierre opcional

**P1 — Alinear header HTTP** con el tipo DID negociado (o documentar explícitamente “solo validación de entrada” en spec pública).

**P2 — Parser `Accept`** con `*/*` y q-values.

**P2 — Sincronizar** `didResolutionMetadata.contentType` con el tipo elegido.

**P3 — `Vary: Accept`** y paridad opcional en index / `did.json`.
