# 2.3 — Verificación JWT y RBAC (a chequiar)

**Tarea BA:** Verificación JWT y RBAC · **Estado entrega:** ✓ DONE (jun 2026)  
**Auditoría:** validate/introspect y RBAC por scopes operativos en `quark-auth`; el gateway valida identidad en rutas protegidas. Lo que sigue es endurecimiento opcional, no bloqueante para el cierre de entrega.

---

## Lo implementado

### quark-auth

**Emisión de tokens.** `POST /v1/auth/token` acepta client credentials o API key. Los scopes solicitados se cruzan con los permitidos del tenant mediante `resolveRequestedScopes`.

**Verificación.** `POST /v1/auth/validate` recibe Bearer JWT o header `x-api-key` y devuelve un `AuthContext` con tenant, scopes y metadatos de cuota.

**Introspección.** `GET /v1/auth/introspect` valida el JWT y expone el mismo contexto (útil para depuración o integradores).

**Revocación.** Existe tabla `revoked_tokens`; `validateToken` rechaza tokens cuyo `jti` figure revocado.

**RBAC en endpoints propios de auth.** `JwtAuthGuard` + `ScopesGuard` + `@RequireScopes(...)` protegen tenants (`tenants:create`, `tenants:read`) y API keys (`apikeys:create`). La utilidad `hasScope` admite match exacto y wildcards (`dominio:*`, `*`).

El seed carga scopes de ejemplo: `tenants:create`, `dids:read`, `dids:write`, `apikeys:create`, etc.

### quark-api-gateway

**Perímetro de autenticación.** `AuthGuard` global consulta `routes.config.ts`: rutas con `requiresAuth: true` exigen JWT o API key; si faltan o son inválidos, responde 401.

**Validación centralizada.** Ante credenciales presentes, el gateway llama `POST /v1/auth/validate` en auth y asigna el resultado a `request.user`.

**Rutas protegidas:** `/index`, `/operations`, `/observer`, `/issuers`, `/verifiers`, `/holders`.

**Rutas públicas (sin auth obligatoria):** `/auth`, `/dids` (resolver).

**Cuota por tenant.** `TenantRateLimitInterceptor` usa `tenantId`, `plan`, `quotaLimit` y `quotaWindowMs` devueltos por validate.

### Flujo documentado

Colecciones Postman y `docs/auth-gateway-mvp.md`: obtener token → enviar `Authorization: Bearer` en rutas con auth. El guard del gateway delega la verificación a auth.

## Gaps detectados (a chequiar)

### 1. Gateway sin RBAC por scope

`AuthGuard` solo comprueba **token válido** (401 si falta o inválido). **No** evalúa si los scopes del JWT autorizan la operación concreta.

Consecuencia: cualquier tenant con JWT válido puede invocar `/v1/issuers`, `/v1/index`, etc., aunque su token no incluya `dids:write` ni scopes de administración.

**Cierre sugerido:** extender `routes.config.ts` con scopes requeridos por prefijo (o decorador equivalente) y devolver 403 cuando `hasScope` falle.

### 2. Servicios downstream sin segunda línea de defensa

`quark-index`, `quark-issuer-service`, `quark-verifier-service`, `quark-holder-service` y `quark-operations` no registran guards JWT propios.

La seguridad depende del perímetro en gateway. Una llamada **directa** al puerto del servicio (3003, 9001, 9002, 9005, …) **no pasa** por validate.

**Cierre sugerido:** asumir red interna cerrada en MVP; si hay exposición, añadir validación local o mTLS + headers firmados.

### 3. Contexto de auth no reenviado al downstream

`GatewayService` reenvía headers del cliente pero **no** inyecta `X-Tenant-Id`, `X-App-Id`, scopes ni `apiKeyId` derivados de `request.user` (detalle en `deuda-tecnica/funcionalidades-pendientes.md`).

Los servicios downstream no pueden aplicar RBAC fino ni completar auditoría con tenant sin duplicar la llamada a validate o confiar en que nadie accede sin gateway.

**Cierre sugerido:** en `AuthGuard` o `GatewayService`, agregar headers de contexto al proxy; los `AuditInterceptor` downstream los consumen.

### 4. Scopes del dominio DID no aplicados en index

El seed define `dids:read`, `dids:write`, `dids:create`, pero ni el gateway ni `quark-index` exigen esos scopes en `GET`/`POST /v1/index/dids`.

**Cierre sugerido:** mapear operaciones index → scope y aplicar en gateway (o en index si se forwardéa contexto).

### 5. Ambigüedad `dids:create` vs `dids:write`

En `funcionalidades-pendientes.md` se anota que no está claro qué operación protege cada scope (`business` tiene `dids:write` sin `dids:create`; `admin` tiene ambos).

**Cierre sugerido:** documento corto operación → scope requerido para todo el SCI.

### 6. Introspect vs validate

`introspect` es GET con Bearer; el gateway solo usa `validate` (POST). Para el MVP alcanza; no hay contrato formal al estilo OAuth 2.0 Token Introspection (RFC 7662) en un doc único.

**Cierre sugerido:** opcional — unificar o documentar cuándo usar cada endpoint.

## Situación por capa (resumen)

En **quark-auth** (endpoints `/v1/auth/tenants`, `/v1/auth/keys`, etc.) hay verificación JWT **y** RBAC por scope.

En **quark-api-gateway** hay verificación JWT en rutas marcadas `requiresAuth`, pero **no** RBAC por scope: basta con token válido.

En **index, operations y observer** no hay verificación propia; confían en que el tráfico llegue solo vía gateway en red interna.

En **issuer, verifier y holder** ocurre lo mismo: sin guards; OID4VC y DIDComm suelen entrar directo al puerto del servicio.

El **acceso directo** a puertos internos bypassa todo el perímetro.

---

## Prioridad de cierre opcional

**P1 — Scopes en gateway.** Definir scopes requeridos por prefijo en `routes.config.ts` y evaluarlos en `AuthGuard` antes del proxy (reutilizar `hasScope` de auth o copia mínima).

**P1 — Contexto en el proxy.** Forward de `X-Tenant-Id`, `X-App-Id` y scopes al downstream para auditoría y RBAC local futuro.

**P2 — Guards en identidad.** Solo si los puertos 900x dejan de ser exclusivamente red interna.

**P3 — Matriz scope ↔ endpoint.** Un MD en `docs/` que cierre la ambigüedad DID y liste cada ruta SCI.
